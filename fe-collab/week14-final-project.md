# 14주차. 최종 프로젝트: 백엔드 팀이 준 API 위에 클라이언트 완성하기

**예상 시간:** 12~16시간 (하루 1시간 세션 16회) | **목표:** 백엔드 팀이 준 도서관 API(`../labs/backend/week25`)를 호출하는 **Next.js 클라이언트**를 처음부터 직접 만든다. 시나리오 13개를 화면에서 재현하고 400·401·404·409 가 서로 다르게 보이게 하면서, 1~13주에서 익힌 것(타입 생성, 에러 분기, 쿠키 인증, 로컬 통합, 캐시 설계, 서버 경계, 테스트, 변경 협의)을 기준표에 맞춰 하나의 결과물로 모은다. 이 주차에는 빈칸도 채점기도 없습니다. **명세와 시나리오만 주어지고, 구현은 직접** 합니다. **마일스톤 점검 주차**입니다.

> 이 주차의 전제입니다. 1~13주를 마쳤고, 특히 6주(타입 생성), 7주(에러 처리), 8주(인증·CORS), 9주(로컬 통합), 10주(데이터 패칭), 11주(서버 경계), 12주(테스트), 13주(협업 실무)의 "먼저 손으로" 와 체크리스트를 끝냈다고 가정합니다. 작업 폴더는 `../labs/my-frontend` 입니다. 저장소에는 만들어져 있지 않으니 직접 만드세요.
>
> 참조 API(`../labs/backend/week25`: Spring Boot, 8080, 데모 로그인 `demo` / `demo1234`, H2 메모리 DB, 세션 쿠키)는 **백엔드 팀이 준 API** 입니다. 소스를 고치지 않고 켜서 호출만 하며, 필요한 정보는 스펙(`openapi.json`)과 응답에서 얻습니다. 이 API 에는 **페이지네이션이 없습니다**(`GET /books` 는 `keyword` 쿼리만 받습니다). 명령은 별도 언급이 없으면 저장소 루트에서 실행합니다. 준비물은 JDK 21, Node 22.12+, pnpm 10+, `curl`, `jq` 입니다.

### 2단계. 설계를 종이에 (40분)

코드 전에 노트에 그립니다. 질문마다 해당 주차 문서에서 답의 재료를 찾을 수 있습니다.

1. **화면과 경로, 호출하는 API.** 어떤 경로에 어떤 화면이 있고 각 화면이 부르는 API 는? 아래 명세의 표로 확정합니다. (2주)
2. **상태 코드 → 표시 종류 표.** 400·401·404·409·그 외가 각각 어떤 표시가 되는가? 이 변환을 **한 곳** 에서만 하게 하려면 어디에 두는가? (7주)
3. **로그인 상태를 어디에 두는가.** 세션 쿠키는 자바스크립트가 못 읽습니다. 그러면 "지금 로그인했는가" 는 어떻게 알고, 여러 컴포넌트가 같은 값을 어떻게 보는가? (8주, 10주)
4. **API 호출 경로.** 프록시(`/api`)로 갈지 직접 호출(CORS)로 갈지, 기본값은 무엇으로 하고 어떻게 바꾸게 할지. (9주)
5. **캐시 키.** 목록, 대출 목록, 내 정보의 키는 무엇이고, 어떤 쓰기가 어떤 키를 무효화하는가? 기본 `staleTime` 은? (10주)
6. **서버 컴포넌트와 클라이언트 컴포넌트의 경계.** 책 상세처럼 서버에서 그릴 화면은 어디까지이고, 상태·이벤트가 필요한 것은 어디까지인가? 서버에서 백엔드를 부를 때 쿠키는? (11주)
7. **테스트의 층.** 어느 규칙을 단위 테스트로, 어느 것을 계약 테스트로, 어느 흐름을 e2e 로 검사할 것인가? (12주)
8. **변경이 왔을 때.** 백엔드가 응답 모양을 바꾸면 어디가 먼저 깨지고, 누구에게 무엇을 물을 것인가? (13주)

프로젝트를 거의 마쳤을 때, 백엔드 팀에서 이런 안내가 왔다고 가정합니다. 참조 API 에는 없는 가상의 변경입니다.

> **[API 변경 예정] 책 목록에 페이지네이션 도입**
> `GET /books` 는 `page`(0부터), `size`(기본 20) 쿼리를 받고, 응답은 배열이 아니라 `{"items": [책...], "total": 전체 개수}` 객체가 됩니다. 다음 주 목요일 배포 예정입니다.

백엔드 파일은 건드리지 않고 스펙 **사본** 을 만들어 그 상황을 흉내 냅니다. 먼저 예측하세요. (a) 이 스펙으로 타입을 다시 생성하면 `pnpm typecheck` 는 어느 파일을 지목하는가? (b) 그때 `pnpm test` 는? (c) 12주의 계약 테스트는 목에서 무엇을 잡는가? (d) 이 변경은 13주의 분류로 호환되는가, 깨지는가?

jq '.paths["/books"].get.parameters += [{"name":"page","in":"query","required":false,"schema":{"type":"integer","format":"int32","default":0}},{"name":"size","in":"query","required":false,"schema":{"type":"integer","format":"int32","default":20}}]
  | .paths["/books"].get.responses["200"].content["application/json"].schema = {"$ref":"#/components/schemas/BookPage"}
  | .components.schemas.BookPage = {"type":"object","properties":{"items":{"type":"array","items":{"$ref":"#/components/schemas/BookResponse"}},"total":{"type":"integer","format":"int64"}},"required":["items","total"]}' \
  labs/backend/week25/openapi.json > $SPECS/paging.json

pnpm -C labs/frontend exec openapi-typescript $SPECS/paging.json -o src/api/schema.d.ts     # 내 프로젝트 폴더로 바꿔 실행
pnpm -C labs/frontend typecheck
pnpm -C labs/frontend test
pnpm -C labs/frontend gen:api && pnpm -C labs/frontend typecheck                          # 원복, 오류 없이 끝나야 함
OPENAPI=$SPECS/paging.json pnpm -C labs/frontend test src/mocks/contract.test.ts          # 12주의 계약 테스트가 있을 때
```

## 명세

### 참조 API 지도

`openapi.json` 에서 읽은 엔드포인트 전체입니다. 이 밖의 요청은 없습니다. 책을 수정·삭제하는 API 도 없습니다.

| 메서드 경로 | 로그인 | 성공 | 실패 |
|---|---|---|---|
| `GET /books?keyword=` | 불필요 | 200 책 배열 (`keyword` 는 제목 부분 일치, 대소문자 무시) | (없음) |
| `POST /books` | 필요 | 201 책 | 400, 401, 409 |
| `GET /books/{id}` | 불필요 | 200 책 | 400 (id 가 숫자 아님), 404 |
| `POST /members` | 필요 | 201 회원 | 400, 401 |
| `POST /loans` | 필요 | 201 대출 | 400, 401, 404, 409 |
| `POST /loans/{id}/return` | 필요 | 200 대출 | 401, 404, 409 |
| `GET /members/{id}/loans` | 불필요 | 200 반납하지 않은 대출 배열 | 404 |
| `POST /auth/login` | - | 200 `{"username"}` | 400, 401 |
| `POST /auth/logout` | - | 204 | (없음) |
| `GET /auth/me` | - | 200 `{"username"}` | 401 |

**페이지네이션이 없으므로** 목록은 전체가 한 번에 옵니다. 페이지 이동 UI 는 이 프로젝트의 요구사항이 아니며, 4단계처럼 "생긴다면 어떻게 되는가" 를 설계 노트로만 다룹니다.

### 화면

| 화면 | 경로 | 기능 | 호출 API |
|---|---|---|---|
| 책 | `/` | 책 목록, 제목 검색(`keyword`), 책 등록 폼 | `GET /books`, `POST /books` |
| 책 상세 | `/books/{id}` | **서버 컴포넌트.** 책 정보와 "로그인한 요청인가" 표시. 없는 id 는 404 화면 | `GET /books/{id}`, `GET /auth/me` |
| 회원 | `/members` | 회원 등록 폼. 등록 결과로 **회원 id 를 보여 줌** (대출 화면에서 씀) | `POST /members` |
| 대출·반납 | `/loans` | 대출 폼(회원 id, 책 id), 내 대출 목록(회원 id 입력 → 반납하지 않은 대출, **반납 버튼**) | `POST /loans`, `GET /members/{id}/loans`, `POST /loans/{id}/return` |
| 공통 머리글 | 모든 경로 | 로그인 폼 / 현재 사용자 + 로그아웃, 화면 이동 메뉴 | `POST /auth/login`, `GET /auth/me`, `POST /auth/logout` |

### 인증

- **읽기(책 목록·검색, 책 상세, 대출 목록)는 로그인 없이**, **쓰기(책·회원 등록, 대출, 반납)는 로그인 후** 에 됩니다. 로그인은 세션 쿠키(`JSESSIONID`)입니다.
- 로그인 전에는 쓰기 버튼이 **눌리기 전에** 막혀 있고 이유를 보여 줍니다. 서버는 어차피 401 이지만 사용자가 눌러 보고 알게 하지 않습니다.
- "로그인 안 함" 은 오류가 아니라 **정상 상태** 입니다. 처음 열었을 때 `GET /auth/me` 가 401 이어도 오류 화면이 나오면 안 됩니다.
- 쓰기 중에 401 을 받으면(세션 만료 등) 화면의 로그인 표시도 즉시 로그아웃 상태가 됩니다.
- 토큰이나 세션 값을 `localStorage` 등에 직접 저장하지 않습니다. 쿠키는 브라우저가 알아서 싣습니다. 서버 컴포넌트에서 백엔드를 부를 때만 코드가 쿠키를 전달합니다(11주).

### 오류 표시

| 상태 | 의미 | 표시 |
|---|---|---|
| 400 | 입력이 잘못됨 | **해당 입력칸 옆** 에 메시지. 폼 위 알림은 띄우지 않음 |
| 401 | 로그인 필요 | 로그인 안내 알림 |
| 404 | 대상이 없음 | "찾을 수 없음" 알림 (서버 화면은 `not-found.tsx`) |
| 409 | 규칙 충돌 (중복 isbn, 이미 대출 중, 3권 한도, 이미 반납) | "충돌" 알림. 입력칸 오류가 아님 |
| 그 외·네트워크 | 서버 꺼짐 등 | "요청에 실패했습니다" 류의 일반 알림 (서버 화면은 `error.tsx`) |

- 서버의 오류 본문은 `{"message": "..."}` 입니다. 그 외 형식(프록시의 500 텍스트 등)도 깨지지 않고 일반 알림이 되어야 합니다.
- 400 의 `message` 는 `필드: 메시지, 필드: 메시지` 형태입니다. **문구에는 의존하지 말고 형식만 가정하세요.** 검증 메시지의 언어는 `Accept-Language` 에 따라 달라집니다(12주).
- 알림의 문구가 같아도, 종류(색·제목·`data-` 속성 등)는 구분되어야 테스트할 수 있습니다.

ok()   { echo "PASS  $1"; }
fail() { echo "FAIL  $1"; FAILS=$((FAILS+1)); }
check() { if [ "$2" = "$3" ]; then ok "$1 ($3)"; else fail "$1 (기대 $3, 실제 $2)"; fi; }
empty() { if [ -z "$2" ]; then ok "$1"; else fail "$1"; echo "$2" | sed 's/^/        /'; fi; }   # 출력이 비어야 통과
status() { curl -s -o /dev/null -w '%{http_code}' "$@"; }

echo "== 1. 타입 생성 (6주)"
pnpm -C $P gen:api >/dev/null 2>&1 && pnpm -C $P typecheck >/dev/null 2>&1 && ok "gen:api 후 typecheck 통과" || fail "gen:api 또는 typecheck 실패"
empty "손으로 쓴 Book/Member/Loan 타입이 없다" "$(grep -rnE "interface (Book|Member|Loan)|type (Book|Member|Loan)[A-Za-z]* = \{" $P/src --include='*.ts' --include='*.tsx' | grep -v schema.d.ts)"
empty "원시 fetch( 호출이 없다 (목·테스트 제외)" "$(grep -rn "fetch(" $P/src --include='*.ts' --include='*.tsx' | grep -v 'mocks/\|\.test\.')"

echo "== 2. 에러 분기 (7주)"
empty "컴포넌트가 상태 코드를 직접 비교하지 않는다" "$(grep -rnE "status *(===|!==) *[0-9]{3}" $P/src/components)"

echo "== 3. 쿠키 인증 (8주)"
empty "localStorage/sessionStorage 를 쓰지 않는다" "$(grep -rn "localStorage\|sessionStorage" $P/src --include='*.ts' --include='*.tsx')"
grep -rq 'credentials: "include"' $P/src && ok "클라이언트가 credentials: \"include\" 로 쿠키를 싣는다" || fail "credentials: \"include\" 가 없다"

echo "== 4. 로컬 통합 (9주)"
[ -f $P/.env.example ] && grep -q NEXT_PUBLIC_API_MOCKING $P/.env.example && ok ".env.example 에 호출 대상 변수가 적혀 있다" || fail ".env.example 이 없거나 변수가 없다"
grep -q 8080 $P/README.md && grep -q 3000 $P/README.md && ok "README 가 8080 과 3000 의 기동 순서를 적는다" || fail "README 에 포트와 기동 순서가 없다"

echo "== 5. 캐시 설계 (10주)"
KEYS=$(grep -rhoE 'queryKey: \[[^]]*\]' $P/src --include='*.ts' --include='*.tsx' --exclude='*.test.ts' | sort -u)
echo "$KEYS" | sed 's/^/        /'
[ "$(echo "$KEYS" | wc -l | tr -d ' ')" -ge 3 ] && ok "서로 다른 queryKey 가 3개 이상이다" || fail "queryKey 가 3개 미만이다"

echo "== 6. 서버 경계 (11주)"
grep -rq "server-only" $P/src && ok "서버 전용 모듈에 server-only 가 있다" || fail "server-only 가 없다"
empty "NEXT_PUBLIC_ 이름에 비밀로 보이는 단어가 없다" "$(grep -rnE "NEXT_PUBLIC_[A-Z_]*(KEY|SECRET|TOKEN|PASSWORD)" $P --include='*.ts' --include='*.tsx' --include='.env*' --exclude-dir=node_modules --exclude-dir=.next)"
ID=$(curl -s $B/books | jq '.[0].id')
if [ "$ID" = null ]; then
  fail "백엔드에 책이 한 권도 없어 서버 컴포넌트 화면을 확인하지 못했다 (먼저 책을 하나 등록)"
elif curl -s -o /dev/null localhost:3000; then
  check "서버 컴포넌트 화면: 있는 책" "$(status localhost:3000/books/$ID)" 200
  check "서버 컴포넌트 화면: 없는 책" "$(status localhost:3000/books/999999)" 404
else
  fail "3000 에 pnpm dev 가 떠 있지 않아 서버 경계를 확인하지 못했다"
fi

echo "== 7. 테스트 (12주)"
N=$(pnpm -C $P test 2>&1 | sed -nE 's/.*Tests +([0-9]+) passed.*/\1/p')
[ "${N:-0}" -ge 15 ] && ok "Vitest ${N}개 통과 (15개 이상)" || fail "Vitest 통과 ${N:-0}개 (15개 이상 필요)"
[ -n "$(grep -rl "openapi.json" $P/src --include='*.test.ts')" ] && ok "스펙을 읽는 계약 테스트가 있다" || fail "계약 테스트가 없다"
E=$(pnpm -C $P e2e 2>&1 | sed -nE 's/^ +([0-9]+) passed.*/\1/p')
[ "${E:-0}" -ge 3 ] && ok "e2e ${E}개 통과 (3개 이상, 실서버)" || fail "e2e 통과 ${E:-0}개 (3개 이상 필요)"

echo "== 8. 협업 (13주): 파일로 남기는 산출물은 사람이 확인"
for f in docs/design-decisions.md docs/change-request.md docs/repro-report.md; do
  [ -f $P/$f ] && echo "FOUND $P/$f" || echo "MANUAL $P/$f 를 작성해 두었는지 확인"
done

[ $FAILS -eq 0 ] && echo "자동 점검: 모두 통과" || echo "자동 점검: 실패 $FAILS 개"
```

## 힌트

정답 코드는 싣지 않습니다. 설계 판단의 단서만 줍니다.

- **상태 코드 변환은 한 곳에.** 화면마다 `if (status === 409)` 가 흩어지면 규약이 깨집니다. 변환 함수 하나와 오류 표시 컴포넌트 하나로 모으세요. 백엔드가 예외를 응답으로 바꾸는 곳이 한 클래스인 것과 같은 구조입니다(7주).
- **400 과 나머지를 가르는 일.** 폼은 "입력칸 옆에 보일 오류" 와 "폼 위에 보일 알림" 을 따로 계산합니다. 같은 오류 객체에서 한쪽만 채워지면 둘이 겹쳐 보이지 않습니다.
- **브라우저 기본 검증을 끄세요.** 폼에 `noValidate` 를 주지 않으면 빈 칸이 서버에 닿기 전에 브라우저가 막아서 400 화면을 볼 수 없습니다.
- **로그인 상태는 한 곳에서 읽고 여럿이 봅니다.** 쓰기 버튼마다 따로 조회하면 요청이 늘고 값이 어긋납니다. 데이터 패칭 라이브러리의 캐시를 "로그인 상태 저장소" 로 쓰면 로그인·로그아웃·401 에서 한 번에 갱신됩니다(10주).
- **MSW 핸들러 경로** 는 브라우저(`/api/...`)와 테스트(`http://localhost:8080/...`)를 둘 다 맞추게 쓰세요(12주).
- **목 핸들러에도 생성 타입을 붙이세요.** 붙은 곳은 스펙이 바뀔 때 `typecheck` 가 알려 주지만, 4단계에서 본 것처럼 붙지 않은 응답은 타입이 어긋남을 못 봅니다. 그 빈틈은 계약 테스트가 메웁니다.
- **테스트 격리.** 목 DB 를 테스트마다 초기값으로 되돌리지 않으면 순서에 따라 결과가 달라집니다.
- **Node 의 `fetch` 는 쿠키를 저장하지 않습니다.** 로그인 상태를 MSW 가 흉내 내는 방식(변수 하나)은 쿠키가 아니라는 한계가 있고, 이 한계는 README 에 적을 만합니다.
- **e2e 의 데이터.** 백엔드 DB 가 실행 중 계속 남으므로 isbn 에 시간값을 섞으면 반복 실행해도 충돌하지 않습니다. 선택자는 CSS 클래스 대신 역할·레이블로 잡으세요.
- **서버 컴포넌트는 쿠키를 자동으로 얻지 못합니다.** 브라우저가 Next 서버로 보낸 쿠키를 서버 코드가 읽어서 백엔드 요청에 실어 줘야 합니다. 안 실으면 오류가 아니라 "로그인하지 않은 요청" 으로 조용히 바뀝니다(11주 실험 A).
- **서버 컴포넌트는 MSW 로 가짜 응답을 줄 수 없습니다.** 서버 경계의 e2e 는 실서버 구성으로만 돌립니다(12주).

## TS 와 비교

최종 프로젝트에서 쓰는 협업 용어를 프론트 용어에 대응시킨 표입니다.

| 백엔드·협업 쪽 | 프론트 쪽에서 닮은 것 |
|---|---|
| OpenAPI 스펙(`openapi.json`) | 두 팀이 공유하는 `.d.ts` 계약 파일. 단, 사람이 쓰는 것이 아니라 서버 코드에서 생성됨 |
| 백엔드 PR 의 계약 층 diff | 라이브러리 메이저 버전 업의 CHANGELOG. 어디를 고쳐야 하는지부터 찾는다 |
| API 변경 요청서 | RFC/ADR. 코드보다 먼저 합의를 남기는 문서 |
| 호환되는 변경 / 깨지는 변경 | 공개 타입에 optional 필드를 추가하는 것 / 필수 필드를 바꾸는 것 |
| 스펙 드리프트 | 타입 선언과 실제 값이 어긋나는 것(`as` 로 덮은 값) |
| 재현 보고서 | 이슈에 붙이는 최소 재현 저장소와 환경 정보 |

## 점검 질문 (자기 설명)

코드를 다 짠 뒤 소리 내어 설명해 보세요.

1. 400·404·409 를 화면에서 다르게 보여 주는 이유는? 사용자는 각각 무엇을 해야 하나요?
2. 타입을 손으로 쓰지 않고 스펙에서 생성한 이유는? 스펙이 바뀌면 무엇이 어디서 알려 주고, 무엇은 알려 주지 못하나요?
3. 세션 쿠키 인증에서 프론트 코드는 쿠키를 어떻게 다루고, 다루지 못하나요? 서버 컴포넌트에서는 무엇이 달라지나요? "로그인했는가" 는 어떻게 아나요?
4. 프록시와 직접 호출 중 무엇을 기본으로 골랐고, 다른 쪽은 어떤 상황에서 필요한가요?
5. 쿼리 키를 어떻게 정했고, 반납 뒤에 무엇을 무효화하나요? 낙관적 업데이트가 `lend` 에는 맞지 않는 이유는?
6. 책 상세를 서버 컴포넌트로 만든 대가는 무엇인가요(MSW, 쿠키, 요청마다 실행)?
7. 내 목이 실서버와 어긋나는 것을 어떤 테스트가 잡고, 어떤 어긋남은 못 잡나요?
8. 4단계의 페이지네이션 안내를 받았을 때 깨지는 변경으로 분류한 근거와, 백엔드에 한 질문은?

1. 400: 내가 입력을 고친다. 409: 입력은 맞지만 규칙상 안 된다(이미 처리됨). 404: 대상이 없다(id 를 확인). 같은 알림이면 사용자가 무엇을 해야 하는지 모른다
2. 두 곳에서 따로 정의하면 어긋난다. 스펙이 단일 출처이면 필드 이름이 바뀔 때 `typecheck` 가 호출부와 타입을 붙인 목 데이터의 오류로 알려 준다. 타입이 못 보는 것은 상태 코드·규칙·타입을 붙이지 않은 목·실행 중의 값이고, 그 몫은 계약 테스트다
3. 브라우저가 쿠키를 자동으로 싣고(`credentials`), `HttpOnly` 라 스크립트는 값을 읽지 못한다. 서버 컴포넌트는 브라우저가 Next 서버로 보낸 쿠키를 코드가 읽어 백엔드 요청에 실어 줘야 한다. "로그인했는가" 는 `GET /auth/me` 를 불러 서버에 묻고 응답(200/401)으로 안다
4. 프록시: CORS 와 preflight 가 없고 쿠키가 단순하다. 직접 호출: 프론트와 백엔드가 서로 다른 도메인으로 배포되고 프록시를 둘 수 없을 때. 이때 CORS 허용 origin 과 쿠키 `SameSite`·`Secure` 를 백엔드와 맞춰야 한다
5. 키는 결과를 바꾸는 모든 입력을 담는다(`["books", keyword]`, `["loans", memberId]`, `["me"]`). 반납 뒤에는 `["loans"]` 접두사를 무효화한다. `lend` 는 서버가 규칙(3권 한도, 이미 대출 중)으로 거절할 수 있는 쓰기라서, 먼저 성공한 것처럼 그리면 되돌릴 일이 잦다
6. 브라우저 서비스 워커가 가로채지 못해 MSW 로 개발할 수 없고, 쿠키를 직접 전달해야 하며, 요청마다 서버에서 실행된다. 대신 첫 화면에 데이터가 담겨 오고 서버 주소·쿠키가 브라우저에 노출되지 않는다
7. 스펙과 응답의 모양·상태 코드는 계약 테스트가 잡는다. 시나리오에 없는 요청, 메시지 문구, 쿠키 속성, 목에만 있는 초기 데이터는 못 잡는다(e2e 가 일부 메운다)
8. 응답이 배열에서 객체로 바뀌어 옛 클라이언트의 `.map` 이 깨진다. 질문 예: `page` 를 안 보내면 전체를 주는가, 정렬 기준과 두 번째 기준, `size` 최대값, `total` 의 비용, 배포 순서(10주의 5-3절 질문 목록)
